## 修复「添加持仓报 readonly database」

### 现象
- UI 添加持仓偶发 500：`sqlite3.OperationalError: attempt to write a readonly database`（INSERT INTO positions）。
- 用户重试后其实都写成功了（positions 表 1-5 条，11:20:05–11:21:46）。

### 根因
- 不是文件权限/锁：外部进程可写，同秒日志表也写成功。
- `src/modules/market/news_flow_scheduler.py` 的 4 个分析 worker 在**未配置 AI 模型**时，每个新闻 id 都会 `_load_analysis_client()` 抛异常 + `analyze_by_id(client=None)` 再抛一次，两次都 `logger.exception` 打整段堆栈。
- DBLogHandler 把每条堆栈写进 `log_entries`：峰值 **2225 条/分钟**（~10MB/分钟），SQLite 写压力把正常业务写事务挤成 SQLITE_READONLY。
- 证据：`log_entries` 中 readonly 出现时间 03:19:41 / 03:21:25 与日志风暴分钟（03:18=2225、03:21=1431）重合。

### 改动
- `news_flow_scheduler.py::_analyze_worker`：同类异常日志节流（`ANALYZE_ERROR_LOG_INTERVAL_SEC=300`），保留「逐条重试加载模型」（配置模型后立即生效）与原有队列语义；重复异常降级为 debug。
- `tests/test_news_flow.py` 新增 `test_analyze_worker_throttles_repeated_client_failures`。全量 `tests/test_news_flow.py`：**53 passed**。
- 重启后：无新 ERROR，readonly 停在 4 条（均在修复前），日志量回落到 2-60 条/分钟。

### 环境备注
- 腾讯 K 线（web.ifzq.gtimg.cn）在本机返回 **501（腾讯 WAF 拦截页 waf.tencent.com）**，带 UA 也一样 → 环境/IP 被 WAF 拦，非代码问题。东财部分接口也偶发断连。

## 排查：事件驱动「采集新闻 → 分析」链路

链路：`news_flow_scheduler`（cron 盘中 */3、盘后整点）→ `news_ingest.ingest_news_sources`（三源）→ 新 id 入 `_analyze_queue`（maxsize 200 / 4 worker）→ `news_analysis.analyze_by_id`（单条 LLM）→ 写回 `market_news` → `strategy_engine` 轮询消费。

### 实测（2026-11-01 12:3x，AI=智谱 glm-5.3-flash）
- 一轮 ingest 串行 **9.56s**：ths 0.63s / wallstreet 4.24s / stockstar 4.05s；三源并行实测 **4.57s**。
- 浪费在主因：**详情页抓了但注定丢弃**
  - wallstreet 热榜 `period=all`，抓 6 篇详情 → 24h 窗口过滤后 **0 条入库**；列表接口已返回 `display_time`+`title` 可直接预过滤。
  - stockstar 抓 6 篇详情 → 仅 1 条新的，**5 条标题重复**（同花顺先收过）；列表页已有 title/publish_date，可用 `news_title_key`+`is_title_duplicate` 预判。
- ths pages=2 时第 2 页返回 0 条（纯浪费请求）。
- 每轮还有 `sleep(0.5)`/`sleep(0.35)` 逐条礼貌间隔，占 wallstreet 约 3s。
- 分析：99 次调用 / 127k tokens ≈ **1286 tokens/条**，其中固定指令块 1259 字符（约 645 token）。5 条批量 prompt 估算 8109→3510 字符（省 57%）。

### 发现的缺陷（未改）
- `_analyze_worker` 的 `_due()` else 分支把 `last_logged` 刷新为 now → 持续异常时完整堆栈**永远不再打印**（与"每 5 分钟一次"意图相反）。
- `ANALYZE_ERROR_LOG_INTERVAL_SEC` 在文件里重复定义两次。
- `_enqueue_catchup` 用 `max(CATCHUP_ANALYZE_LIMIT, ANALYZE_QUEUE_MAXSIZE)`=200，会占满队列使新采集 id 全部 skipped；`CATCHUP_ANALYZE_LIMIT=8` 实际失效。
- 模型不可用时：worker 每条仍调 `analyze_by_id(client=None)` → 再 load 一次配置 + 一条 INFO 日志，200 条/5 分钟空转。
- `_analyze_row_by_id` 在 `await` LLM 期间一直持有 Session（长读事务，阻碍 WAL checkpoint）。
- 强信号新闻无推送/不触发研究：`market_news` 只被 `strategy_engine`/`context_scheduler` 轮询读取。

## 事件驱动「采集→分析」第二轮优化（13:30-13:55，已改+已验证）
改前实测证据（`scheduler_job_runs`）：04:00-04:51 跑了 8 轮采集 + 4 轮补扫，全是凌晨无差别频率；周末同样每 15 分钟。

### 已修（4 项）
1. **分析调用没有自己的超时**：`AIClient` 里 `AsyncOpenAI(**kwargs)` 没传 timeout → 默认 600s + max_retries=2，模型侧挂起时单个 worker 能被钉半小时，200 条队列只涨不跌。
   → `news_analysis.ANALYZE_TIMEOUT_SEC = 90` + `_complete_with_timeout()` 用 `asyncio.wait_for` 包一层；批量和单条都走它。
2. **批量调用失败后逐条回退**：原 `_analyze_chunk` 的 except 只记日志，随后 `elif await _analyze_snapshot(...)` 逐条再调 → 一批 5 条变成 6 次调用，还把每条的 3 次重试额度一起烧掉。
   → 只有 `_is_item_specific_error()`（`BadRequestError`/400-422，可能是某条内容触发）才逐条定位；超时/连接/5xx/鉴权视为整批性故障：整批放弃、**不扣 fail_count**、不逐条，等下轮补扫。
3. **4 个 worker 无熔断**：模型链整体挂时 4 个 worker 各自反复撞同一堵墙。
   → 模块级熔断（`_breaker_until`/`_fail_streak`，多 worker 共享=全局熔断）：连续 3 次调用失败 → 30s 起指数退避至 300s，任一调用成功即清零；`_analyze_worker` 在 `queue.get()` **之前**检查 `analysis_breaker_remaining()` 并等待，避免把 id 一条条取出来再失败。
4. **强信号推送两个坑**：a) `_rate_limited()` 检查与 `_sent_at.append()` 之间隔着 `await notifier.notify()`，4 worker 并发能同时通过检查 → 「每小时 6 条/间隔 30s」被突破；b) `await self._push_strong_signals(...)` 在 worker 循环内串行 await，webhook 慢会卡住队列消费。
   → `news_signal_alert._push_lock`(asyncio.Lock) 包住整个 `push_if_strong`（低频动作，串行无成本）；scheduler 侧新增 `_schedule_strong_signals()` 用 `create_task` 投递，`shutdown()` 里 cancel `_push_tasks`。

- 单条分析 prompt 1566 字，其中固定指令（rules `news_analysis.md` 961 字 + `BATCH_OUTPUT_SPEC` 445 字）占 **96.3%**。`llm_token_usage` 里 news_analysis 113 次调用：**70 次单条 / 41 次两条 / 2 次三四条 / 0 次五条**——「批量 5 条」从未达成。
- 原因：4 个 worker 各自 `await queue.get()`，一次采集入队的 5 条被 4 个 worker 各抢一条，`_drain_batch` 只能捡剩下的。日志里 04:03:12 同一秒 4 次调用就是证据。

### 已改（3 项）
1. **取批串行化 + 攒批等待**（`news_flow_scheduler`）
   - 新增 `_collect_lock`（`asyncio.Lock`）：只有取批阶段串行，分析调用仍并发 4 路。
   - `_drain_batch(first_id)` → `async _next_batch()`：取到第一条后，已排队的一律立刻取走；队列暂空时最多等 `BATCH_LINGER_SEC=1.5s`，攒够 `BATCH_ANALYZE_SIZE=5` 就走。
   - 用 `qsize` 轮询（`BATCH_POLL_INTERVAL_SEC=0.05`）而不是 `wait_for(queue.get())`：后者超时取消 `get()` 时可能刚好取走一条又丢掉，会静默丢新闻。
   - 取消时对已取出的 id 补 `task_done()`，避免 shutdown 时 `join()` 挂住。
   - `stats()`/启动日志加 `batch_linger_sec`。
2. **瞬时故障不再烧重试额度**（`news_analysis._analyze_snapshot`）
   - 改前：任何异常都 `_record_failure(+1)`。队列只剩一条时 chunk 长度=1，走的就是这条路径 → 模型抖动 3 轮就把新闻永久标成 `analyze_fail_count=3`，恢复后 `list_unanalyzed` 不再捞它。
   - 改后：只有 `BadRequestError`(400/422，确实是这条内容的问题) 计入额度；超时/连接/5xx/鉴权 → `_trip_breaker()` 但不扣额度。调用成功即 `_reset_breaker()`（原来单条成功不清熔断）。
3. **批量结果整体不可解析时先对半拆**（`_analyze_chunk(depth=)`）
   - 改前 1 条都解析不出就逐条重打：1 次失败放大成 N 次，还把每条的额度烧掉。
   - 改后：`len<=2` 且 depth=0 → 逐条（小批量便宜且能救回，保持原语义）；`len>2` → 对半拆一次（5 条：1+2 次调用而不是 1+5）；拆完仍不可解析 → 整批留待下轮、不扣额度、不逐条。

## 事件驱动第六轮：5 项全部落地（15:35-16:00，已改+已重启）

### 1. 标题键：首句过短时累积后续句子（`news_keys.news_title_key`）
- 新增 `_ORIGINAL_TITLE` 先截掉「（原标题：…）」，再按句切分；首句 ≥8 字行为完全不变（历史 key 不受影响）。

### 2. 判重窗口：只对「本身就是旧文」的候选启用入库时间锚
- 关键取舍：**不能无条件双锚**。无条件按入库时刻再比一次，会把「A股开盘：三大指数集体低开」这类每日模板标题互相压制（实测两个既有用例立刻挂掉）。
- 最终规则：候选的 `news_time < now - 12h`（本身是旧文）时，才额外按「入库时刻」比一次。转载的旧文重发正好落在这个条件里，正常时效的新闻完全不受影响。
- 落点：`NewsDedupSnapshot.blocked` / `is_title_duplicate` / `IngestDedupIndex.is_duplicate_title` 三处统一；`TitleIndex` 加 `add_anchors`（同一条记录按发布时间 + 入库时间双入桶）。

## 机会链路第三轮优化（12 条 + 1 个连锁问题）

前两轮改完"流程通不通"，这轮修"指标能不能用"。核心结论：胜率此前仍不可信，原因与前两轮不同。

### P0 评估口径
- `plan_outcome.evaluate_plan_path` 增加 `fill_mode`（open_in_band / fall_back / bounce_up）。**成交当日只判"成交之后才可能发生"的那一侧**：高开回落成交当日不判目标（成交前的高点被误记为 hit_target），低开反弹成交当日不判止损（成交前的低点被误记为 hit_stop）。实测两个方向都错且相反。
- `_build_plan` 目标改由阻力位/ATR 决定，**不再用 `mid + 1.5×risk` 抬目标凑 R:R**。R:R 不足时收紧止损；收进 `PLAN_STOP_MIN_PCT` 以内仍不够则 `plan_rr_ok=False` 降级。新增 `PLAN_TARGET_MAX_PCT=15%`。
- 风险基准统一用 `entry_high`（最差成交价），`_plan_quality` 同步并留 0.999 浮点容差；`_build_plan` 反推止损时给 1.002 余量，避免产出 1.4998 这种卡线值。
- `factor_eval` 加 `_point_in_time_filter()`（`snapshot_date < POINT_IN_TIME_START` 或 `meta.point_in_time=true`），并把 `date.today()` 换成 `app_now()`；horizon 日历日按 7/5 折算 +2 天缓冲；返回增加 `rows / unique_symbols / point_in_time_samples`。

## 第四节：两个已知遗留的处理（absolute_score clamp / 样本不足虚高）

### 1. absolute_score 封顶 0-100
- `_score_suggestion` 里 `absolute_score` 改为 `clamp(composite, 0, 100)`；`composite_score` 保持未封顶（排序/IC 用）。
- `_format_signal` 读出口再夹一次：历史快照里仍留着 145.78 这类旧值，只靠重算不保险；同时把返回的 `score_breakdown.absolute_score` 一起改写，避免顶层与 breakdown 给出两个数（旧版分别写 136.05 / 145.78，来源是 payload 写每行 composite、breakdown 写股票级最高值）。
- 取舍：composite 实测上限 145.78（base 可到 100 再叠加 alpha/catalyst/source_bonus 和 weight 0.95~1.18），封顶后强信号会在这个字段上并到 100。因为前端不读该字段、排序走 `rank_score`、原始值留在 `composite_score`，信息没丢，只是挪到了内部字段。

### 2. 百分位改中点口径
- `_normalize_actionable_rank`：`idx/(n-1)` → `(idx + 0.5)/n`，等价于"偏离中位按 (n-1)/n 收缩"。
- n=1 时旧口径除零退回 `pct=1.0` ⇒ 当日唯一可执行票必然是 100 分。实测 2026-11-01 可执行只有 600519（4 条策略行），4 行全读 100。新口径 87.5（中位），理论上界 `100 - 12.5/n`。
- 副作用受控：映射恒在 (75, 100) 开区间，`paper_trading` 的 85/75 分档与 `MIN_RANK_SCORE_FOR_ENTRY=75` 不受影响；`to_ai_score` 只在 n 极小的日子从 10 降到 9。

### 验证
- `test_strategy_rank_normalize.py` 20 passed：改写 3 例期望值、新增 `test_single_actionable_stock_is_not_topped_out` 与 `test_format_signal_clamps_legacy_absolute_score`。
- 真实数据：接口 `absolute_score` max 由 145.78 → 100.0，可执行 `rank_score` 100 → 87.5，`rank_pct=50`。
- 全量 **22 failed / 1570 passed**，失败清单与基线一致（均为 Windows/网络/环境类，已在基线上复现）。

### 追加：absolute_score 取消封顶（用户要求）
- 上一节给 `absolute_score` 加的 `clamp(0,100)` 已撤销，打分段与读出口都恢复为未封顶值。
- 保留的部分：`_normalize_actionable_rank` 里 payload / breakdown 统一写股票级最高值（旧版两处分别是 136.05 / 145.78）；`_format_signal` 读出口把 breakdown 的 absolute_score 收敛到顶层读到的值。
- 口径定稿：`absolute_score` = 未封顶加权合成分（实测上限 145.78，可 >100），跨日可比、衡量绝对强度；要 0-100 的展示分用 `percentile_score` / `rank_score`。文档化写在 `_score_suggestion` 注释与 `_format_signal` 返回处。
- 测试改名 `test_format_signal_keeps_unbounded_absolute_score`，断言 145.781 原样输出且两处收敛。
